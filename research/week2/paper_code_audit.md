# Week 2 paper--code audit

Reference paper: *Adaptive Chunking: Optimizing Chunking-Method Selection for RAG*, arXiv `2603.25333v1`. Code evidence refers to commit `ea87ce8`.

## Executive finding

The repository is sufficient to start a core reproduction from the 33 pre-parsed CLAIR documents, but the current one-command RAG path should **not** yet be treated as an exact reproduction of paper Table 5. Two blocking mismatches change the experimental treatment: the code's Adaptive path can select over all post-processed methods rather than only the four paper candidates, and its RAG baselines are exported from `small_merged` rather than raw chunks.

## Direct answers to the four audit questions

1. **Does the selector improve downstream RAG or only proxy metrics?** The paper reports better LLM-judged retrieval completeness and selective answer correctness, but current code cannot yet provide a protocol-faithful rerun because of candidate/baseline mismatches. There is no evidence-label retrieval evaluation.
2. **Is there document leakage?** The original rule has no fitted parameters, so conventional train/test leakage is not the primary issue. The larger validity issue is evaluation on one corpus with generated questions and no held-out-document analysis. The group's learned selector must use GroupKFold/document splits.
3. **Is BI page-dependent?** It does not read page numbers directly. It is nevertheless nearly tautological for raw page splitting because page boundaries and gold block boundaries come from the same parsed representation; the all-document audit strongly supports this concern.
4. **Does better retrieval lead to better answers?** Table 5 moves both metrics in the same direction, but correctness is conditional on answering and retrieval completeness is itself LLM-judged. This is association, not a robust causal demonstration. Report overall utility and evidence-based retrieval metrics.
